# 撒网打鱼｜开发计划与验收

> 实施进度：首个可玩版本v0.1.0已开发；本文保留v0.4设计基线，已实现和待验收项目见[07号记录](07_首版实现与验证记录.md)。

2026-10-12；v0.4；当前只完成调研和设计，没有开发完成项。详细范围见[PRD](02_产品需求文档_PRD.md)、[TDD](03_开发设计文档_TDD.md)、[美术动效规格](05_美术与动效设计规格.md)与[生物及撒网机制](06_生物多样性与撒网机制.md)。本版扩充生物并升级按住/松手和容量机制，继续提高正式美术与动态制作投入。

## 1. 推荐推进顺序

核心可玩原型与视觉关键画面尽早推进；批量精修前完成10–15秒实际渲染动态切片，确认水体、鱼和收网看起来成立。然后展开10种可捕/6种观赏生物、界面与完整内容。可以复用旧作工程，但首个里程碑不能只交一套捕鱼皮肤。

| 阶段 | 工作包与输出 | 完成判据 | 估算投入 |
|---|---|---|---:|
| A 基线准备 | 独立工程、记录来源提交、删军事分支、基础配置与新存储key | 新旧数据互不影响，离线启动，工程检查可运行 | 0.5–1 人日 |
| B 核心可玩原型 | 三网位、真实多鱼实体、网状态机、仲裁、90秒与结算、简化船鱼网画面 | 没有随机假命中，能完整玩一局，核心不变量通过 | 2.5–4 人日 |
| C 手感与获得感 | 三类群形/交错、三段节奏、10种可捕/6种观赏生物差异、单网反馈、稀有鱼机会 | 同seed策略对比完成，首次5人测试发现的问题有处理结论 | 2–3 人日 |
| D 精修视觉与产品闭环 | 关键画面/动态切片、精修海湾与10种可捕/6种观赏生物、光影、船网动画、音频与完整页面功能 | P0完整且达到视觉规格；真实尺寸动态与可玩流程均可审查 | 8–12 人日 |
| E 验证与交付 | 浏览器/容器/真机、画质档/最大动效压力、8–12人三局测试、修复、审计打包 | 阻断问题归零，视觉与性能有同场景证据，同ZIP可追溯 | 2.5–3.5 人日 |
| 合计 | 单人串行估算 | 见估算前提 | **15.5–23.5 人日** |

估算前提：已有工程可正常复用；一处精修分层场景、10种可捕/6种观赏生物部件或少量关键帧、参数化网形、共享光影/水花；无后端、完整3D、真实流体、全套高帧逐帧动画或额外主题。D阶段细分：关键画面/切片1–1.5、正式资源与动效5–7.5、产品闭环2–3人日。以上是规划估算，不是外部美术报价或日历承诺；复杂原创角色动画、大改美术方向或设备等待需另计。v0.1的7.5–12与v0.2的11.5–18.5人日分别对应更早的简化视觉/六鱼范围，均已被本版替代。

## 2. 每阶段的具体任务

### A：隔离产品身份

1. 从已记录提交复制必要源码，建立本项目自己的版本管理与来源说明。
2. 配置、名称、图标、存储命名空间、产物名称全部独立。
3. 移除鱼雷、连爆、生命、补给与十波旧数值，以及对应军事UI/音效。
4. 保留固定时间步、多指输入、平台适配、构建和校验结构。

阶段输出：可运行的独立壳与代码差异清单。不对旧游戏目录执行写操作。

### B：先把一网做正确

1. 实现多条独立鱼、固定位置下沉、按住沉网/松手展开、六格容量、回收和到船计分。
2. 实现重叠网归属、阶段内事件顺序、快鱼碰撞与视图范围一致。
3. 实现三网位与单网控制绑定、按下/松手/系统取消、暂停与最后一网尾收。
4. 用原型画面验证：鱼进了网、网里有几条、网何时回到船，均看得懂。

阶段输出：完整90秒可玩原型、核心测试结果、至少一段正常操作录屏。临时演示种子需标注，不把固定满网演示当真实体验分布。

### C：验证过程，而非追求总鱼数

1. 生成紧密/疏散/单鱼与交错机会，验证每15秒存在浅层机会。
2. 对照站桩固定浅网、移动固定浅网、带有限观察的深度/时机策略，补固定深网诊断；记录跳过出生和鱼的可触达性。
3. 首轮5人快速试玩，问“刚才为什么有/没有捕到”“下一网想怎么改”。
4. 按空网原因、满网频率、等待和玩家决策改参数；冻结一组版本后再测试。

阶段输出：体验诊断、数值变更原因、原始人数与每网分布。若“观察没有收益”“收网像自动刷”，暂停扩大内容，先解决核心。

### D：完整主题与跨局动力

1. 先交静态关键画面与10–15秒实际渲染动态切片，验证一小获、一空网和一次构造的丰收；再制作精修海湾、10种可捕/6种观赏生物部件、木船、鱼篓、网格与收绳。此项中的早期视觉验证前置到B/C期间，工时仍计入D，不重复计算。
2. 替换爆炸/警报，完成声音解锁、独立开关和静音体验。
3. 完成教程、图鉴、最佳一网、本机纪录、局内小目标与结算建议。
4. 完成全阶段存档、重复结算防护、设置、用户主动成绩卡保存/分享。

阶段输出：功能候选、分层精修资产、动态切片、实际游戏录屏、资产登记、产品流程截图与声音样例。视觉效果图不能代替动态实现，程序几何占位不能作为最终美术验收。未经许可的素材不能进入正式包。

### E：使用同一候选包验证

1. 完成范围内单元/集成/浏览器检查、资源清单与包审计。
2. 创服模拟器完整流程；Android/iOS扫码运行同一ZIP；补目标HarmonyOS/iPad机型。
3. 8–12人连续三局，验证PRD获得感与重玩信号。
4. 缺陷修复、版本冻结、重新生成受影响检查，不重复无关检查。
5. 交付候选ZIP、图标、文档、测试报告和已知问题。上传/发布根据届时用户授权执行，不在本轮设计工作中操作。

## 4. 策略对照方法

至少100个固定seed，每个seed使用四种策略；同版本、同出生计划，公开策略能访问哪些信息。站桩固定浅网固定x且每网在y=360张开；移动浅网左右往返且固定360展开；固定深网始终980展开；观察策略使用屏内目标位置、方向、粗略速度与可读占格，不能读取未来出生列表。

对照记录：得分、完成网次、每网个数/占格直方图、空网/满载比例、平均占位、无收获间隔、鱼种多样性、稀有捕获、计划/实际出生和跳过数。不得授予无限网、无敌或强制掉落来得出正常难度结论。

观察策略读取程序数据仍比真人精确，结果仅说明机制是否允许策略收益；如果需要“上界策略”读取未来，则单独列出，不与正常策略混称。≥25%中位数差异是初始判断门槛，不能替代“玩家能解释和享受”的访谈。

## 5. 真人试玩记录模板

每位玩家记录：代号、是否玩过旧作、设备/系统/小红书版本、教程是否需要帮助、三局分数和每网分布、最长无收获区间、主动重玩行为及原因。

每局只问三项：

1. 哪一网最有感觉，为什么？
2. 哪次空网不理解，原本想网哪群？
3. 再玩一次会改什么，是否愿意再玩？

先记录行为再问意见，不向玩家暗示“你是不是觉得很解压”。报告保留失败与零收获样本，不只挑最好录屏。

## 6. 数值调优顺序

1. 先解决输入、碰撞与画面不一致，再讨论手感。
2. 再调浅层机会、群间空隙、游速和提前量；判断空网是否可解释。
3. 再调网口/展开窗口/回收时间；一次改变一类参数，记录版本。
4. 再调鱼种分值与单网倍率，避免靠夸大分数掩盖过程贫乏。
5. 最后调图鉴、小目标、结算建议等重玩层。

不能通过给每网随机补鱼解决零收获，也不能通过随机让鱼逃脱限制满网。收获分布应来自布局与行为。

## 7. 性能与设备证据

每次报告写清设备型号、OS、宿主版本、包SHA256、画质档、测试步骤、持续时间、帧耗时与异常。目标为实际目标设备稳定30FPS；记录中位数与P95帧耗时，不能只报平均值。后台/恢复、最大网鱼、成绩卡生成与十分钟多局是重点。

创服模拟器、普通Chrome、桌面WebKit、iPhone真机、小红书容器和HarmonyOS属于不同证据层；不能互相替代。若目标设备未到位，明确标待验证，不写“全机型通过”。

## 8. 交付清单与完成定义

- 独立源码、来源提交和最终差异清单。
- 正式离线候选ZIP、独立图标、构建版本与SHA256。
- PRD/TDD/实施文档、原创资产登记与必要许可。
- 核心测试、策略对照、真人体验与真机记录。
- 官方包审计结果、已知问题、恢复/回滚说明。

工程完成：P0实现且必要检查通过。体验成立：基本获得感、技巧收益与多局变化有初步证据，未处理的核心阻断问题为0。平台可提交：候选包规则检查通过、要求的容器与真机验证有记录。平台审核通过/实际上线是之后独立状态。

当前文档阶段的交付不包括实现、游戏包或上线，也不声称已完成以上测试。
